### OpenAI API Response Calls
> [!NOTE]- Quickstart:
> 
```javascript
import OpenAI from "openai";
const client = new OpenAI();

const response = await client.responses.create({
  model: "gpt-5.6",
  input: "Write a short bedtime story about a unicorn.",
});

console.log(response.output_text);
```

Response API shows higher promise in intelligent and consistent results, thus Causerie will utilise it.
> [!NOTE] Simple Response API Call:
```javascript
import OpenAI from "openai";
const client = new OpenAI();

const response = await client.responses.create({
  model: "gpt-5.6",
  reasoning: { effort: "low" },

    {
      role: "developer",
```

`instructions` parameter only applies to the current request. If you are managing conversation state with `previous_response_id`, the `instructions` used on previous requests will not be present in the context.

Roles are as follows:
	`developer`  - Instructions provided by developer, prioritized ahead of user messages.
		`developer` messages provide system's rules and business logic, like a function definition.
	`user`           - Messages are instructions provided by an end user, prioritized behind user messages
		`user` messages provide inputs and configuration to which `developer` instructions are applied, like arguments to a function.
	`assistant`  - Messages are generated by the model
#### Model Reasoning By Feature
General conversation should only require low effort, but tasks such as translation, corrections, and goal fulfillment should be medium or high (**re-evaluate later**).

### API Auth
Provide API credentials with the HTTP Bearer Authentication:
`Authorization: Bearer OPEN_API_KEY_OR_ACCESS_TOKEN`

### Debugging Requests
> [!NOTE] API Meta Information
`openai-organization`: The organization of the request.
`openai-processing-ms`: Time taken processing API request.
`openai-version`: REST API version used for request.
`x-request-id`: Unique identifier for API request (for troubleshooting).

Rate limiting headers exist, but are intuitive by name.
You may supply your own x-request-id by including the header `X-Client-Request_Id` (must be <512 characters, may use any ID format)

### Webhooks
Webhooks are HTTP requests sent by OpenAI to a URL you specify when certain events happen during the course of API usage.

These include:
`response.completed` - sent when a background response has been completed
**id**: string - ID of event
**created_at** number - unix timestamp (seconds) when model response was completed
**data** { id } - event data payload
**type** "response.completed" - type of event
**object** optional "event" - object of event, always event

```json
{
  "id": "evt_abc123",
  "type": "response.completed",
  "created_at": 1719168000,
  "data": {
    "id": "resp_abc123"
  }
}
```

`response.cancelled` - sent when a background response has been cancelled
See above for model

`response.failed`
See above for model

`response.incomplete`
Happens when a background response has been interrupted. See above for model

`batch.completed`, `batch.cancelled`, `batch.expired`, `batch.failed` - see above
`fine_tuning.job.succeeded`, `fine_tuning.job.failed`, `fine_tuning.job.cancelled` - see above
`eval.run.succeeded`, `eval.run.failed`, `eval.run.canceled` - see above

`realtime.call.incoming` - sent when API SIP session is available for Realtime acceptance. First successful Realtime or Live accept endpoint selects the runtime surface

`live.call.incoming` - sent when API SIP session is available for Live acceptance. First successful Realtime or Live accept endpoint selects the runtime surface.

### Context Management
Two relevant modes of context management:
1. Local Context - code can access during a run: dependencies or data needed by tools, callbacks like onHandoff, and lifecycle hooks
2. LLM-Visible Context - what LLM can see when generating a response

Use **local context** for things like:
* Data about the run (user name, IDs, etc.)
* Dependencies such as loggers or data fetchers
* Helper functions

Example of **local context** in use:
```javascript
import { Agent, run, RunContext, tool } from '@openai/agents';
import { z } from 'zod';

interface UserInfo {
  name: string;
  uid: number;
}

const fetchUserAge = tool({
  name: 'fetch_user_age',
  description: 'Return the age of the current user',
  parameters: z.object({}),
  execute: async (
    _args,
    runContext?: RunContext<UserInfo>,
  ): Promise<string> => {
    return `User ${runContext?.context.name} is 47 years old`;
  },
});

async function main() {
  const userInfo: UserInfo = { name: 'John', uid: 123 };

  const agent = new Agent<UserInfo>({
    name: 'Assistant',
    tools: [fetchUserAge],
  });

  const result = await run(agent, 'What is the age of the user?', {
    context: userInfo,
  });

  console.log(result.finalOutput);
  // The user John is 47 years old.
}

main().catch((error) => {
  console.error(error);
  process.exit(1);
});
```

`runContext<T>` is a wrapper around the app-defined context object. In practice, you use:
* `runContext.context` for mutable app state and dependencies
* `runContext.usage` for aggregated token/request usage of the current run
* `runContext.toolInput` for structured input when the current run is executing inside `agent.asTool()`
* `runContext.approveTool(...)` / `runContext.rejectTool(...)` for programmatically updating approval state

Only `runContext.context` is the app-defined object. Other fields are runtime metadata managed by the SDK.


Use **LLM-visible context** for including information additional to conversation history. To make additional information available you have the following options:
1. Add it to the Agent `instructions` (AKA system or developer message). Can be a static string or a function that receives the context and returns a string.
2. Include it in the `input` when calling Runner.run(). This is similar to `instructions`, but lets you place the message lower in the __chain of command__.
3. Expose the additional information through function tools so the LLM can fetch that info on demand.
4. Use retrieval or web search tools to ground responses in relevant data from files, databases, or the web.


### Model Context Protocol (MCP)
MCP standardizes how applications provide tools and context to LLMs. It is an open protocol, and acts like a USB-C port for AI applications in that it provides a standardized way to connext AI models to different data sources and tools. In other words, MCP is a standardized interface between LLM applications and external systems.

The three types of MCP servers supported by OpenAI:
* Hosted MCP server tools (remove MCP servers used as tools by OpenAI Responses API)
* Streamable HTTP MCP servers (local or remote servers that implement the streamable HTTP transport)
* Stdio MCP servers (servers accessed via standard I/O - simplest)

**Tools are like the following**:
* get_weather(city)
* search_database(query)
* create_calendar_event(...)

**Resources are like the following**:
* company://policies/pto
* project://source-code

**Prompts are like the following**:
* summarize_customer
* diagnose_bug

**Causerie should implement a stdio MCP server**
